# Запуск в реальном отеле: интеграции, сервер, доступы

## 1. Доступы, которые нужно получить

## 2. Серверная часть (предлагаемый стек)

- **API**: Node.js 22 + TypeScript, Fastify, валидация zod, OpenAPI.
- **БД**: PostgreSQL 16 (заявки, чаты, конфигурация, события, аудит). Партиционирование `events` по месяцам.
- **Очереди и планировщик**: Redis + BullMQ: отправка в Bitrix24 с повторами, напоминания по SLA, опрос Bnovo, загрузка офлайн-конверсий.
- **Хранилище медиа**: S3-совместимое (Yandex Object Storage) + CDN для видео и фото.
- **Секреты**: переменные окружения / Lockbox. В браузер ключи не попадают никогда.
- **Админка**: этот же React-код, данные через API вместо localStorage.
- **Мониторинг**: логи в JSON, Sentry (ошибки фронта и API), алерт если очередь Bitrix24 не разгребается > 5 мин.

### API

Публичное (для скрипта на сайте, CORS только домен отеля, rate limit по IP и visitor_id):
```

POST /api/public/events                        батч событий
POST /api/public/leads                         заявка: honeypot, время заполнения, дедуп 10 мин, SmartCaptcha при подозрении
POST /api/public/chat                          начать чат
POST /api/public/chat/:id/messages             сообщение гостя (ответ ИИ стримится через SSE)
```

Вебхуки: `POST /hooks/bitrix24`, `POST /hooks/telephony`, опрос Bnovo по расписанию (или вебхук, если доступен).

## 3. Интеграции: как устроено

### Bnovo
- **Наличие и тарифы**: сервер запрашивает Bnovo API на даты и гостей, отдаёт категории с ценой. Если API недоступен, квиз и чат переходят к заявке на индивидуальный подбор (уже реализовано в UI).
- **Передача дат**: ссылка в модуль `reservationsteps.ru/rooms/index/<UID>?dfrom=dd-MM-yyyy&dto=…&adults=…` + UTM (формат взят из `availability.gs`).
- **Сопоставление**: каждые 5 минут `GET /api/v1/bookings` → совпадение по телефону/e-mail с лидом за 30 дней → `bookings.lead_id`, статус и сумма. Только такие брони идут в «Подтверждённые» и «Выручку».
- **Уведомления о бронях**: сервер считает агрегаты (брони за сегодня с заездом на выходные, доля броней от 3 ночей, загрузка на даты) и отдаёт только сигналы выше порога. Если данных нет, виджет молчит.

### Bitrix24
- `crm.duplicate.findbycomm` по телефону/e-mail → при совпадении комментарий в существующий лид/контакт, иначе `crm.lead.add` (формат виден в карточке заявки → «Показать, что уйдёт в Bitrix24»).
- Поля: имя, телефон, e-mail, источник, UTM_*, ответственный (`ASSIGNED_BY_ID`), комментарий с ответами квиза и выбранным временем, ссылка на переписку.
- Переписка чата: `crm.timeline.comment.add` по мере диалога.
- Напоминания: `tasks.task.add` ответственному при просрочке SLA, повтор каждые N минут.
- Статусы обратно: исходящий вебхук → статус заявки в панели (новая / в работе / дозвонились / не дозвонились / забронировано / отказ).

### Яндекс Метрика
- Скрипт вызывает `ym(counter, 'reachGoal', 'v125_<виджет>_<действие>')`: просмотр, открытие, начало заполнения, заявка, переход в бронирование.
- Подтверждённые брони с выручкой: офлайн-конверсии по ClientID (`v125_booking_confirmed`), только когда бронь сопоставлена с лидом.

### ИИ-консультант
- Модель получает: системный промпт с правилами, подтверждённые записи базы знаний, инструменты `get_availability`, `create_lead`, `handoff_to_manager`.
- Ограничения: цены и наличие только из ответа инструмента; при отсутствии ответа в базе знаний - передача администратору; ПД собираются только после явного согласия.
- Выключатель ИИ в панели переводит все новые чаты на людей (реализовано).

## 4. Безопасность и ПД

- Согласие на обработку ПД в каждой форме, фиксируется время и версия текста согласия.
- Хранение ПД в РФ, шифрование диска и бэкапов, доступ к телефонам и перепискам только у ролей с доступом к заявкам.
- Антиспам: honeypot, минимальное время заполнения, дедуп контакта 10 минут, rate limit, SmartCaptcha при аномалиях.
- Роли проверяются на сервере; аудит всех изменений настроек и заявок.
- Скрипт на сайте: Shadow DOM, один корневой элемент, без глобальных стилей; при ошибке API виджеты скрываются, сайт не ломается.
- Срок хранения: заявки без брони - 1 год, переписки - 1 год, события - 13 месяцев (настраивается).

## 5. Порядок запуска

1. Сервер + БД + приём заявок, Bitrix24 (без него заявки будут теряться в отдельной системе).
2. Скрипт на сайт: обратный звонок, мультикнопка, генератор заявок. Цели в Метрике.
3. Bnovo: квиз и чат с наличием, сопоставление броней, выручка в аналитике.
4. ИИ-консультант после наполнения и подтверждения базы знаний.
5. Уведомления о бронированиях, персонализация, A/B-тесты (нужен трафик: от ~1000 показов на вариант).
6. Телефония (автоматический callback) - если отдел не успевает перезванивать вручную.

Перед запуском сверить: обещанное время перезвона с фактической скоростью ответа отдела (Главная → «Скорость ответа против обещания»).
